SEC-01 Subscription Member endpoints can cross User boundaries Authorization is checked on the parent inconsistently, while child lookup and deletion use unscoped IDs. P0 · Critical

Evidence

Subscription Member listing accepts a Subscription ID without first resolving the scoped parent. Subscription Member deletion verifies the supplied Subscription, but does not verify that memberId belongs to it before deleting by ID.

Impact

A user who learns foreign identifiers could read another user's members or delete a foreign Subscription Member using one of their own Subscription IDs.

Target state

  • Resolve the owned Subscription before every authenticated child operation.
  • Query/delete Subscription Members by both Subscription ID and Subscription Member ID.
  • Keep the Public Subscription View on an explicit capability-authorized query path: resolve the token first, then load children for only that resolved Subscription.
  • Add two-User negative integration tests returning 404 and a public-view regression test.
OPS-01 Railway sleep/wake cycles leave stale database connections Frontend failures and Quarkus exceptions line up with PostgreSQL connections being closed underneath the pool. P0 · Critical

Evidence

Production logs show repeated backend-unreachable and 500 responses, plus SQLState 08006, EOF, and “connection has been closed” errors. All three services currently have Railway Serverless enabled.

Impact

The application can wake successfully but serve failed requests until invalid pooled connections are discarded. User actions may fail in bursts after idle periods.

Target state

  • Retain serverless sleep to control idle RAM cost.
  • Validate/recycle connections and retry only safe initial reads.
  • Pass a repeatable idle → sleep → wake reliability test.
DATA-01 Payment Record idempotency is enforced only in application code The check-then-insert sequence can race because the intended tuple has no database uniqueness constraint. Deployed · verified

Evidence

Billing checks existence and then inserts a record inside the loop. Migration V4 creates no unique index for the Subscription, billing date, and Subscription Member tuple.

Impact

Concurrent generation requests can create duplicate payment obligations despite the method's documented idempotency guarantee.

Target state

  • Add one new append-only Flyway migration: a unique index on (subscription_id, billing_date, member_id) for non-null members and a unique index on (subscription_id, billing_date) where member_id IS NULL.
  • Fail the migration with a diagnostic query if historical duplicates exist; never edit V4.
  • Serialize generation by pessimistically locking the owned Subscription before reading nextBillingDate; retain the indexes as the final invariant.
  • Test concurrent generation against PostgreSQL.
SEC-02 Public subscription capability tokens are written to logs Both the public route and service record the token used to access shared financial information. P0 · Critical

Evidence

Token values are interpolated into frontend error messages and backend INFO logs for both successful and failed public subscription lookups.

Impact

Anyone with log access may reuse a bearer-style capability URL. Tokens also spread into retained operational data and debugging exports.

Target state

  • Never log raw capability tokens.
  • Correlate with stable event names, HTTP status, and the resolved Subscription ID; do not add a token fingerprint.
  • Document redaction rules for credentials and financial identifiers.

03 · Recommended sequence

Reduce risk before refactoring.

The order is intentional: first close security and availability gaps, then create the safety net required to simplify the code confidently.

0

Protect User data and stabilize production

  • Fix Subscription Member listing/deletion authorization and add cross-User regression tests.
  • Stop logging public subscription tokens; define a credential-redaction policy.
  • Retain Railway Serverless and absorb cold starts with a bounded safe-read retry.
  • Run a 20-cycle idle/wake soak test and keep write requests single-attempt.
1
Safety net Next iteration · P1

Make bad changes difficult to ship

  • Add CI for backend tests, PostgreSQL/Flyway integration tests, frontend checks, and production builds.
  • Add Payment Record uniqueness with a new Flyway migration and concurrency coverage.
  • Make Docker builds deterministic and fail-fast.
  • Switch Railway's backend health check to readiness.

  • Replace per-row service lookups with projections or batched queries.
  • Add query-count expectations for transaction, debt, and subscription lists.
  • Classify logs by actionable event; alert on database disconnect bursts and readiness failures.
  • Clean ignored Quarkus configuration and expected WorkOS inactivity messages.

Split the frontend along feature boundaries

  • Introduce a typed server-side API client with shared authentication and error mapping.
  • Extract the largest route components incrementally, one tested interaction at a time.
  • Centralize DTOs and pure financial/display helpers.
  • Add component and end-to-end coverage before broad page rewrites.

  • Use immutable Railway IDs and document safe preflight checks; never rely on the stale local project link.

  • Review this plan after each phase and close findings only against exit criteria.

A01 Scope Subscription Member operations without breaking the public capability path Repository contract · P0 · S · no dependency ready-for-agent

Authorized scope

Change SubscriptionService, the Subscription input/output ports, PanacheSubscriptionMemberRepository, SubscriptionResource, PublicSubscriptionResource, and adjacent domain projections and tests. Follow ADR-0011, ADR-0014, and ADR-0018.

Fixed implementation

  • Authenticated Subscription Member listing must first resolve the Subscription through subscriptionRepository.findById(subscriptionId); return 404 when the Subscription is foreign, deleted, or absent.
  • Replace unscoped Subscription Member primary-key lookup/deletion with repository methods that constrain both subscription.id and Subscription Member ID. A mismatched pair returns 404 and changes no shares or rows.
  • Add PublicSubscriptionViewUseCase#getByToken(String) and a focused application query service returning a public-view projection. It resolves the capability token first and loads Subscription Members, Payment Records, and Contact names only for that resolved Subscription. Acceptance & verification

  • User A receives 404 when listing User B's Subscription or pairing A's Subscription with B's Subscription Member ID; no row is deleted.
  • A valid public token still returns the same Public Subscription View; an invalid token returns 404.
  • Add these cases to CrossUserIsolationTest and a new public-resource test, then run cd backend && ./mvnw test.

A03 Retain Railway Serverless and prove safe idle recovery Railway contract · P0 · S · no dependency retry deployed · 1/20 passed

Precondition & implementation

  • Run the fixed Railway authentication and explicit-target preflight above. Do not relink or mutate if any ID/name differs.
  • Retain sleep behavior for frontend, backend, and PostgreSQL to control idle RAM cost.
  • Retry backend network failures and transient 502/503/504 responses only for GET/HEAD, with a bounded wake budget.
  • Never automatically retry a write request after an ambiguous failure.

Soak procedure

  • Across 20 backend/frontend idle-to-active recoveries, issue a harmless read through the public frontend and record timestamp, response status, and latency.
  • After each recovery, query bounded backend logs for SQLState 08006, EOF, “connection has been closed,” and datasource acquisition errors.
  • Do not retry a failed probe before recording its first result; retries would hide the user-visible failure.

Completion signal

All 20 first attempts avoid user-visible 500s and targeted backend logs contain no stale-connection error. Attach the probe table, final Railway config read-back, and a keep/disable recommendation for sleep based on observed cold-start latency.

Bounded logs contained no stale-connection signature. See the A03 evidence record. Keep serverless sleep enabled and continue the revised series from 1/20.

A05 Make Payment Record generation idempotent under concurrency Repository contract · P1 · M · depends on A04 ready-for-agent

Migration contract

  • Compute the next Flyway version at implementation time and add exactly one new migration; never modify V4 or another existing migration.
  • Before creating indexes, use a PostgreSQL DO block to detect and report duplicate logical tuples so deployment fails with a useful diagnostic instead of deleting or merging financial history automatically.
  • Create one unique index on (subscription_id, billing_date, member_id) where member_id IS NOT NULL, and a second on (subscription_id, billing_date) where member_id IS NULL.

Concurrency contract

  • Add a repository operation that loads the caller-owned Subscription with a PostgreSQL pessimistic write lock before reading nextBillingDate.
  • Hold the lock for generation and date advancement in one transaction. Keep the database indexes as the final invariant.
  • Do not swallow arbitrary constraint violations or mark a failed transaction successful.

Acceptance & verification

  • Two genuinely concurrent transactions generating the same Shared Subscription produce one Payment Record per Subscription Member and advance the date once.
  • The same test for a Personal Subscription proves that the null-Subscription-Member case produces exactly one Payment Record.
  • Sequential re-triggering remains a no-op. Run cd backend && ./mvnw test against PostgreSQL.

  • After the fixed target preflight, create a production backend notification that fires on three datasource/readiness failures within five minutes and uses the workspace's existing operational destination.
  • Use Railway's API/MCP when exposed; otherwise use the signed-in Railway dashboard. Read back the rule name, target service ID, threshold, and destination.
  • If no operational destination exists, do not invent one or send a test externally: apply needs-info with the missing destination as the only blocker.

Completion signal

A controlled non-production readiness failure triggers one test notification, while a healthy startup contains no unrecognized-property warning or raw capability token.

  • Create docs/operations/railway.md with the immutable production IDs above, authentication/context checks, bounded log commands, deployment terminal-state rules, and rollback ownership.

Restore drill contract

  • Read and record the latest production Postgres backup metadata. Require a successful backup no older than 24 hours and at least seven days of retention; otherwise apply needs-info before creating resources.
  • Restore the latest backup into a temporary isolated non-production service/environment named restore-drill-YYYYMMDD. Never restore over or write to production.
  • Verify row counts for root tables, foreign-key integrity, and Flyway history through the production migration version using read-only SQL.
  • After evidence is saved, delete only the explicitly created restore-drill resources and read back their removal. This cleanup is authorized by this contract; no other resource deletion is allowed.

Completion signal

A second agent can follow the committed runbook without unstated decisions, the restore checks pass, production remains unchanged, and no temporary paid resource remains.

05 · Exit criteria

How improvement is measured.

These outcomes prevent the roadmap from becoming an open-ended rewrite.

Security & data integrity

  • All nested-resource operations bind child identity to an owned root entity.
  • Cross-user access tests cover both reads and mutations.
  • No raw secrets or capability tokens appear in logs.
  • Database constraints back every documented idempotency guarantee.

Production reliability

  • Twenty repeated idle/wake cycles complete without a user-visible 500.
  • Readiness reflects database availability.
  • Connection-failure bursts produce an actionable alert.
  • A current database backup can be restored successfully.

Release confidence

  • Backend tests, migrations, frontend checks, and production builds are required.
  • Docker dependency installation cannot fail silently.
  • Flyway migrations are tested against PostgreSQL and remain append-only.
  • Dependency advisories have owners and explicit dispositions.

Readability & maintainability

  • Routes use one typed backend client and one error mapping strategy.
  • Large pages delegate coherent interactions to tested feature components.
  • List endpoint query count is bounded rather than proportional to item count.
  • Warnings in a healthy production startup are understood and intentional.

Private backend boundary
