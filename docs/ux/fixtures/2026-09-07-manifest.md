# Fixture manifest — Slice 0A

Companion to the [UX execution plan](../2026-09-07-execution-plan.md) and its [audit](../2026-09-07-audit.md).

Scope: **Slice 0A only**. The 0B scenarios — underfunded Spending Budget, Saving Goal states, owner-participation variants, partial contributions, the credit-in-favor/unpaid-statement combination, and `FX-DASH-NEG-01` — are not implemented here.

Every value below is synthetic and invented for verification. No fixture reads, seeds, or modifies development or production data, and none of the figures are taken from records observed during the audit.

## Where the fixtures live

| File | Purpose |
|---|---|
| `frontend/tests/fixtures/scenarios.ts` | Scenario data, stable IDs, and expected values |
| `frontend/tests/fixtures/backend.ts` | In-process `fetch` replacement with failure injection |
| `frontend/tests/fixtures/clock.ts` | Fixed instants, time zones, and a scoped clock |
| `frontend/tests/fixtures/server.ts` | Local HTTP fixture backend for browser verification |
| `frontend/tests/fixtures.test.js` | Tests proving determinism, isolation, and failure behavior |
| `frontend/tests/setup.ts` | Bun preload (`bunfig.toml`) stubbing SvelteKit's `$app/*` virtual modules and the type-only `effect` shims, so a loader or action that pulls in `sveltekit-superforms` can run under `bun test` |

`scenarios.ts` is authoritative. If a value changes there, this manifest follows it rather than being maintained independently.

## Setup and reset

There is nothing to seed and nothing to clean up. Scenarios are in-memory constants; `loadScenario` returns a deep copy, so a test that mutates its data cannot affect any other test. "Reset" is simply constructing a new fixture backend, or calling `reset()` on an existing one to clear recorded requests and post-construction failure injection.

```bash
cd frontend
bun test tests/fixtures.test.js   # the fixture harness itself
bun test                          # the whole suite
```

### Clock and time-zone inputs

| Clock | Instant (UTC) | Time zone | User calendar day |
|---|---|---|---|
| `MEXICO_CITY_MIDDAY` | 2026-09-07T18:00:00Z | America/Mexico_City | 2026-09-07 |
| `MEXICO_CITY_EVENING` | 2026-09-08T04:30:00Z | America/Mexico_City | 2026-09-07 |
| `TOKYO_SAME_INSTANT` | 2026-09-08T04:30:00Z | Asia/Tokyo | 2026-09-08 |

`FX-DATE-BOUNDARY-01` uses `MEXICO_CITY_EVENING`, where the UTC day is already 8 September but the User's day is 7 September. Against that day it provides an obligation yesterday (2026-09-06: credit statement 9302 due, subscription 9403), today (2026-09-07: subscription 9404), and tomorrow (2026-09-08: subscription 9405). `withFixtureClock` pins `Date.now()` for the duration of a callback and always restores the real clock, including on throw. It is a test helper only: nothing pins the clock of a browser pointed at the fixture server.

The truth table these dates are evaluated against belongs to decision D2 and slice 1D; 0A supplies the dates, not the statuses.

## Failure injection

Failures are injected in the harness only. No live service is disrupted, and no request leaves the process.

```ts
const backend = createFixtureBackend('FX-TRACK-ACTIVE-01', {
  failures: { 'GET /api/dashboard/summary': { kind: 'status', status: 500 } },
});
// pass backend.fetch where a loader expects SvelteKit's fetch
```

- `{ kind: 'status', status }` resolves with an error response, for a backend that answers but fails.
- `{ kind: 'unreachable' }` rejects with a `TypeError`, matching a network failure. This is in-process only; the browser fixture server has no equivalent (see below).
- `failRoute` / `healRoute` toggle a route mid-test, for Retry behavior.
- A route the scenario does not declare **throws**. A loader that requests something unplanned fails visibly instead of quietly receiving an empty list — the exact confusion 1A-loader has to remove.
- `backend.requests` records every call, so a test can assert which requests were made and that no others were.

Failure scenarios prepared for Phase 1: failed dashboard summary (fabricated zero), unreachable box summary, and partially failed subscription sections (members succeed while payments fail).

## Browser verification

The browser harness is available now and reuses the same scenario data, so a fixture's numbers cannot differ between tests and the screen.

```bash
cd frontend
bun run tests/fixtures/server.ts FX-BAL-OVERRESERVED-01     # 127.0.0.1:8099
FIXTURE_FAIL='GET /api/dashboard/summary=500' \
  bun run tests/fixtures/server.ts FX-BAL-OVERRESERVED-01   # error state
```

The server binds `127.0.0.1` explicitly, so invented balances are never published on the machine's network.

Then, in a second shell:

```bash
cd frontend
BACKEND_URL=http://127.0.0.1:8099 TEST_AUTH_BYPASS=true bun run dev
```

`TEST_AUTH_BYPASS` is the repository's existing non-production local flag in `src/hooks.server.ts`; it is refused when `NODE_ENV=production`. It requires no additional routes of its own — the bypass session is synthesized in the hook and never calls the backend. Nothing here changes production authorization, and because `BACKEND_URL` points at the local fixture process, the browser session cannot reach or modify shared development data.

What every authenticated page needs regardless of scenario: `+layout.server.ts` requests `GET /api/user/preferences`, `GET /api/boxes/summary` and `GET /api/accounts/status` on each navigation. The fixture server answers `/api/user/preferences` from a harness default (the same values as the loader's own defaults, `timeZone: America/Mexico_City`) so the shell is not silently degraded in scenarios about something else; a scenario that declares the route overrides it. `/api/boxes/summary` and `/api/accounts/status` are scenario data: where a scenario omits them the setup redirect does not fire, and since Slice 1A-loader the header balance chip shows its unavailable state with a Retry action instead of a fabricated 0.00. Both are harness artifacts of an undeclared route rather than findings.

The clock is not pinned in the browser. Scenario clocks are inputs to the fixture data and to `withFixtureClock` in tests; a page served by this server renders against the machine's real wall clock. Any date-boundary check in the browser has to come from the fixture's own dates, not from an assumed "today".

Exercised so far: 1A-loader's root checks used `FIXTURE_FAIL='GET /api/dashboard/summary=500'` and `GET /api/subscriptions/{id}/payments=500`. Because `FIXTURE_FAIL` is fixed at startup, "healing" a route in the browser means restarting the server without it and pressing Retry; there is no in-browser equivalent of `failRoute`/`healRoute`.

Known limits of the browser harness, to be closed by the slice that needs them:

- The fixture server is read-only. Actions that POST/PUT/DELETE return 404 unless the slice adds those routes, so it currently supports viewing normal and error states rather than exercising write flows.
- Each scenario declares only the routes its listed acceptance cases need. A page that reads something else will show the loader's error state and log the missing route key; add it to the scenario in `scenarios.ts` at that point.
- The debt scenarios declare only the debt detail page's own reads, so browsing one shows the shell's balance chip in its unavailable state — the same undeclared-route artifact described above, not a 1B finding. Recording a payment in the browser needs a `POST /api/debts/{id}/payments` route the fixture server does not yet have; that write path is covered by the in-process action test instead.
- `FIXTURE_FAIL` takes HTTP error statuses only (400–599); a non-status value is rejected at startup. A `fetch` handler cannot drop a connection — throwing from one yields a 500 — so there is no browser-side "unreachable" mode rather than a misleading imitation of one. Use 500 for an immediate error, and 503 as the documented surrogate for an unavailable backend; note that `fetchBackendWithWakeRetry` retries 502/503/504 GETs through its full delay ladder (~16s) before the loader sees the failure. Genuine network rejection stays in the in-process backend, where loaders are tested.
